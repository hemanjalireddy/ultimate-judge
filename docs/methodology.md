# Methodology v1

## Design

Generation and judging are separate. A benchmark contains frozen movie facts,
candidate text and generator identities. The judge sees only the request, facts,
criteria, and anonymous displayed answers. Model IDs and human annotations never
enter the judge prompt. Run IDs hash the full benchmark, configuration, system
prompt and generation settings; request budget and file location are operational
settings and do not change run identity. Trials have stable condition-specific IDs.

Each condition is evaluated in both orders. Which order executes first is shuffled
with a seeded RNG; three repeated trials are the default. Calls are independent
conversations and sequential (concurrency one). This does not eliminate provider
drift or correlation. Input/output snapshots establish procedural reproducibility,
not identical future API responses.

### Position and self-preference

The original c0/c1 pair is the shared baseline. A/B are displayed positions;
metrics map them back to c0/c1 before comparison. Self-preference is eligible only
when exactly one candidate was generated by the judging model, and uses decisive
baseline judgments only. Template/demo generators are not represented as real LLM
outputs. A generator-by-judge table also groups results by reviewed quality label
where supplied. This is descriptive stratification, not causal adjustment.

### Verbosity and style

For **each** original candidate, construct a separate comparison: c0 is that
original answer, c1 its transformed version. These condition-local IDs differ
from the baseline pair; the `target` field identifies the source candidate.
Verbosity repeats the exact answer once. Style adds Markdown blockquote formatting.
Both are stored for review; neither is automatically approved. A reviewer must
record identity and an assertion of equivalent facts/useful information.

Unreviewed conditions may be executed for inspection but are excluded from the
controlled preference metrics. Formatting can legitimately improve readability;
repetition can legitimately reduce usefulness. These are measured preferences
under specified transformations, not conclusive evidence of unfair bias.

## Metrics and denominators

Every proportion exposes numerator, usable n, and contributing case count.

| Metric | Numerator / denominator |
|---|---|
| Position consistency | Same canonical outcome, including Tie/Tie / complete valid swapped baseline pairs |
| Decisive flip rate | Opposite canonical winners / complete pairs with two decisive verdicts |
| Tie transition | Exactly one tie / complete valid swapped baseline pairs |
| Repeatability | Equal canonical outcomes / all unordered valid trial pairs with identical case, judge, condition, source target and order |
| First-position preference | Displayed A / decisive baseline judgments |
| Reviewed verbosity/style preference | Transformed c1 wins / valid judgments with approved equivalence review; ties remain in denominator |
| Own-answer preference | Judge's own candidate wins / eligible decisive baseline judgments |
| Reference agreement | Canonical outcome matches reference / valid baseline judgments with approved, non-uncertain human labels |
| Tie rate | Ties / valid judgments across selected conditions |
| Invalid output rate | Malformed/incomplete outputs / recorded observations |
| API failure rate | Exhausted or permanent API errors / recorded observations |

Partial swapped pairs do not enter paired metrics. API failures and invalid
outputs are never ties. Invalid and API-failure rates are **per trial**, not per
transport retry. Metadata tables expose latency (including backoff), token totals
when returned, and the number of responses for which usage is available. Zero
known token usage with zero covered responses does not mean zero provider cost.

Rates may weight cases unequally when some responses are missing. Missingness can
bias comparisons. Filters can remove one side of a pair; usable n then decreases.
Legacy single-experiment summaries retain their original definitions (including
ties in own-answer rate) and must not be pooled with benchmark metrics.

## Uncertainty

95% percentile bootstrap intervals use 1,000 draws, sampling benchmark-case IDs
with replacement and retaining every observation within each sampled case. The
seed is the saved run seed (42 by default). No interval is reported with fewer
than two contributing cases. These intervals address case sampling variation,
not dataset provenance errors, model drift, or human-label uncertainty.

The benchmark is small, deliberately selected, and shares movies across some
cases. Case clustering does not capture every source of dependence. Intervals
can be degenerate at boundary outcomes; this does not demonstrate certainty.
No significance claims or automated behavioral regressions are reported.

## Failure and reproducibility policy

Groq transport retries only connection errors, 408, 409, 429 and 5xx responses:
at most three attempts. Transient errors use exponential backoff with jitter;
429 responses honor Retry-After (seconds or HTTP date), waiting up to five minutes
with visible countdown updates. Longer limits save a UTC retry time and pause.
If Retry-After is absent, the fallback is 60 seconds, not a confirmed reset time.
Conservative per-model spacing uses estimated prompt tokens plus an output allowance;
it cannot guarantee staying below variable token limits. Authentication
and invalid requests are not retried. Malformed judgments are recorded as invalid
rather than re-prompted until a desirable verdict appears.

The benchmark conservatively reserves three live requests before dispatch; unused
reservations are released for valid responses. Errors/crashes can overcount the
budget, never undercount it. Resume skips valid and invalid model outputs, but retries
API errors at the same stable comparison ID, including failures from earlier runs.
Previous failures are retained in `failed_attempts` before the replacement is saved;
completed model judgments are never regenerated. The active observation rates use
the latest attempt, while history records previous API failures separately.
Resuming before a recorded retry time makes no new requests. Increase the budget to continue a budget-
limited run without changing its ID. For intentional repeat measurements change
the seed and retain both runs. A process crash can leave a `.lock` file: remove
that exact lock only after confirming no process still owns the run.

Mock judgments always choose displayed A. They are a deliberately biased fixture
for verifying mapping and metrics, not simulations calibrated to real models.
